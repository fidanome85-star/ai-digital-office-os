# AI DIGITAL OFFICE OS v1.4
## Technical Integrity Review & Required Closure Patch

**Baseline:** AI DIGITAL OFFICE OS v1.3 Consolidated Master  
**Review date:** 2026-08-30  
**Purpose:** Deep consistency audit of the v1.3 PDF, with no weakening of the approved architecture.

## Executive verdict

The v1.3 document is **substantially stronger than v1.2 and should NOT be discarded**. It closes the major v1.2 narrative/schema gaps, adds tenant isolation, RBAC closure, durable workflow records, agent messaging, tiered memory, artifact lineage, NFR/SLO targets and sequence diagrams.

However, after a deeper cross-layer audit, I would **not yet call it implementation-lock perfect**. The remaining issues are concentrated in the relationship between the blueprint, relational schema and control-plane API.

The most important blockers are:

1. Missing authoritative Project Registry.
2. Missing true Agent Version model.
3. Missing Agent Run / Model Run records required by artifact lineage.
4. RLS only enabled on four tables instead of the complete tenant-scoped surface.
5. Missing persistent MCP/tool registry.
6. Missing model-evaluation history.
7. Missing authoritative cost/usage ledger.
8. Missing deployment/release registry.
9. OpenAPI lifecycle coverage is incomplete.
10. Several API schemas are narrower than the SQL model.

These are **structural closure issues**, not a reason to redesign the Office. The correct action is a v1.4 integrity patch that preserves v1.3 and closes these contracts.

## Required v1.4 rule

Do not create a second competing architecture. Preserve v1.3 clauses 1–58 and add the missing data/API/operational closure. The final implementation baseline must have one canonical domain model, one permission model, one tenant boundary and one artifact lineage.

## CRITICAL — Project Registry is missing

**Finding:** The blueprint and API use project_id throughout, but the SQL schema has no project_registry/projects table. This breaks referential integrity and prevents the Project Factory from having an authoritative project record.

**Required closure:** Add project_registry with tenant_id, project_id, name, type, constitution_version, lifecycle_state, risk_level, owner, repository_ref, environment policy, created_at and updated_at. Add project endpoints to the API.

## CRITICAL — Agent versioning is structurally incomplete

**Finding:** agent_registry uses agent_id as the sole primary key while the acceptance criteria require ACTIVE agent updates to create a new version rather than overwrite the active record. A separate agent_versions table is required.

**Required closure:** Add agent_versions keyed by agent_version_id, with agent_id, version, specification_hash, prompt_version, model_policy, permissions snapshot, evaluation result, status and lineage. Make activation point to a specific version.

## CRITICAL — Artifact lineage references undefined run entities

**Finding:** artifact_registry contains agent_run_id and model_run_id, but there are no agent_runs or model_runs tables. Full lineage therefore cannot be reconstructed from the relational model.

**Required closure:** Add agent_runs and model_runs, plus foreign keys from artifacts, routing/audit records and task attempts.

## CRITICAL — RLS is only partially implemented

**Finding:** The SQL explicitly says to extend RLS later and enables it on only four tables. That is not sufficient for a strong tenant-isolation baseline because prompts, policies, approvals, workflows, messages, memory, secrets, feature flags and RBAC junctions remain exposed to service-layer mistakes.

**Required closure:** Enable RLS on every tenant-scoped operational table and define both USING and WITH CHECK policies. Keep system-template NULL tenant rows explicitly constrained to template-only tables.

## HIGH — Message idempotency is not stored

**Finding:** The specification requires idempotency for agent messages, but agent_messages has no idempotency_key column or uniqueness rule.

**Required closure:** Add idempotency_key and UNIQUE(tenant_id, idempotency_key). Store delivery attempts and duplicate-handling outcome.

## HIGH — Model evaluation history is missing

**Finding:** model_registry has only a current evaluation_score. The blueprint promises versioned, rerunnable model evaluation, but there is no evaluation-run history.

**Required closure:** Add model_evaluation_runs and model_evaluation_metrics. Preserve benchmark version, model version, evaluator version, score and timestamp.

## HIGH — Cost/usage ledger is missing

**Finding:** Cost governance is defined, but there is no authoritative usage ledger for tokens, requests, provider/model cost or budget consumption.

**Required closure:** Add usage_events/cost_ledger with tenant, project, task, agent, provider, model, input/output usage, estimated/actual cost, currency, timestamp and billing status.

## HIGH — Deployment/release records are missing

**Finding:** The blueprint has deployment, release, rollback and artifact lineage concepts, but deployment_ref is only a free-text field.

**Required closure:** Add deployment_registry and release_registry with immutable release identifiers, artifact references, environment, strategy, health state, approval, rollback target and timestamps.

## HIGH — MCP tool registry is missing

**Finding:** MCP is the explicit interoperability standard, but there is no persistent registry for MCP servers/tools, capabilities, allowed actions or tool versions.

**Required closure:** Add mcp_server_registry, tool_registry and agent_tool_bindings. Bind permissions and policy decisions to stable tool IDs.

## HIGH — OpenAPI is still not a complete control-plane contract

**Finding:** The document says the API is full, but key lifecycle operations are absent or incomplete: project creation, workflow creation/cancel, artifact creation, agent activation/version selection, message send, provider/model registry management and cost/usage queries.

**Required closure:** Expand /v1 with the missing resource lifecycle endpoints and explicit request/response/error schemas. Protect every endpoint with bearer auth and required scopes.

## HIGH — OpenAPI schemas do not fully match SQL

**Finding:** AgentRecord omits several operational fields present in SQL. Artifact and feature-flag schemas are also narrower than the database model.

**Required closure:** Generate API schemas from a canonical domain model or maintain a schema-diff gate in CI so SQL and OpenAPI cannot drift.

## MEDIUM — Authentication contract needs stronger implementation detail

**Finding:** JWT bearer authentication is specified, but issuer, audience, JWKS rotation, token expiry, required scopes and service-vs-human claims are not fully defined.

**Required closure:** Add issuer/audience/JWKS requirements, required scopes, clock-skew policy, token lifetime, service identity claims and key-rotation behavior.

## MEDIUM — Session management is mentioned but not modeled

**Finding:** Layer 9 says session management exists, but there is no session/refresh-token or session-revocation model.

**Required closure:** Either explicitly delegate sessions to the external identity provider and document that boundary, or add session_registry and revocation semantics.

## MEDIUM — Policy decision history deserves a first-class record

**Finding:** Audit payload can hold policy results, but routing and policy behavior are important enough for deterministic incident reconstruction to deserve structured records.

**Required closure:** Add policy_decision_records and routing_decision_records linked to task/run IDs, with candidate alternatives and rejection reasons.

## MEDIUM — Acceptance claims must distinguish specification from measured evidence

**Finding:** The PDF correctly says the numeric SLOs are starting baselines, but the checklist sometimes reads like an achieved production state.

**Required closure:** Label every acceptance item as TARGET, TEST REQUIRED or VERIFIED. No item may be marked VERIFIED until an actual test run produces evidence.

## MEDIUM — The master PDF is a consolidated specification, not implementation

**Finding:** The document honestly states that no infrastructure-as-code, provider contracts, penetration-test results or credentials are included. This is correct, but the next implementation package needs explicit environment contracts.

**Required closure:** Keep v1.4 as the specification baseline and create a separate implementation phase package containing IaC, deployment topology, secrets integration, real provider adapters and executed test evidence.

## What is already strong and should remain unchanged

- Owner/CEO/Executive Manager/Assistant Manager hierarchy.
- Agent Factory and controlled agent lifecycle.
- Capability-based model routing.
- OpenAI/GPT, Anthropic/Claude, Google/Gemini, Moonshot/Kimi, local models and future-provider adapter concept.
- Central Policy Engine and GREEN/YELLOW/RED governance.
- Durable workflow/event-history concept.
- Tiered memory and pgvector/HNSW direction.
- Artifact immutability and lineage concept.
- Independent QA and security gates.
- Bounded self-healing.
- MCP for tool interoperability and optional A2A-style external interoperability.
- Concrete NFR/SLO starting baselines.
- Explicit honesty clause distinguishing specification from running production evidence.

## Final decision

**v1.3 = architecturally strong, but not yet implementation-lock perfect.**

**v1.4 = required integrity closure.**

After the listed blockers are closed and the SQL/OpenAPI/domain-model consistency tests pass, the blueprint can be treated as the implementation master baseline. This does not mean the application itself is built; it means the specification contracts are sufficiently closed to begin controlled implementation.
